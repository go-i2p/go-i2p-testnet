# Monitoring Discovery: routers, I2PControl, and the testnet launch path

Findings from reading the README, `main.go`, the config generators, the
dockerfiles, and live probes against real routers (i2pd 2.60.0 from Alpine
3.22 — the same package the `i2pd-node` image installs — and upstream
`github.com/go-i2p/go-i2p` master). This is the input for the dashboard work;
see `docs/monitoring-verification.md` for the end-to-end results.

## Divergences from the task prompt (repo wins)

1. **Branch.** The prompt says "work directly on `main`". This repository has
   no `main` branch: `origin/HEAD -> origin/experimental` and the only shared
   branch is `experimental`. All dashboard commits therefore go to
   `experimental` (the repo's default branch).
2. **No compose/launch script.** The prompt suggests "script, Makefile, or
   compose service". There is no compose file and no launch script; the launch
   path is the interactive CLI in `main.go` (`start`, `add …`, …) driven by the
   `go-i2p-testnet` binary (`make build && ./bin/go-i2p-testnet`). The
   dashboard is integrated there as one extra component of the same process,
   not as a parallel launcher.
3. **Routers did not expose I2PControl at all** before this change. Enabling
   it required config changes *inside this repo* (the routers' generated
   configs), which is in scope, so the "stop and ask" condition does not
   apply. Details below.

## How routers start

Everything is orchestrated by the Go CLI in `main.go` against the Docker API
(no docker CLI, no compose):

- `start` creates the bridge network `go-i2p-testnet` (`Internal: true`,
  subnet `172.28.0.0/16`, see `lib/docker_control/network.go`) and the shared
  volume `go-i2p-testnet-shared`.
- `add i2pd_router` / `add goi2p_router` assign `172.28.0.(routerID+1)`,
  generate a config, put it on a per-router volume, and start a container
  named `router-i2pd-N` / `router-goi2p-N`.
- The router list lives only in memory (`main.go`: `var routers []Router` with
  `ID`, `Type` (`"i2pd"` / `"goi2p"`), `Name`, `ContainerID`, `VolumeName`,
  `IP`). Nothing is hardcoded per-router; the dashboard reads this list.

### i2pd routers

- Image `i2pd-node` = `alpine:3.22` + `apk add i2pd` (currently **i2pd
  2.60.0**), CMD `i2pd --conf=/var/lib/i2pd/i2pd.conf
  --datadir=/var/lib/i2pd`
  (`lib/dockerfiles/i2pd-node.dockerfile`, `lib/i2pd/container.go`).
- Config generated in `lib/i2pd/config.go` (`GenerateRouterConfig`) via
  `gopkg.in/ini.v1` from the `I2PDConfig` struct: `netid=5`,
  `reservedrange=false`, `host=<container IP>`, webconsole `[http]` on
  `127.0.0.1:7070` (inside the container), reseed disabled.
- I2PControl: i2pd supports an `[i2pcontrol]` section (`enabled`, `address`,
  `port`, `password`, `cert`, `key`; default port 7650, default password
  `itoopie`, HTTPS with a self-signed cert auto-generated into the datadir as
  `i2pcontrol.crt.pem` / `i2pcontrol.key.pem`). **It was not enabled in the
  testnet config** — i2pd's default for `i2pcontrol.enabled` is false.

### go-i2p routers

- Image `go-i2p-node` builds go-i2p from upstream master inside Docker
  (`lib/dockerfiles/go-i2p-node.dockerfile`); the container runs
  `go-i2p --bootstrap.type local …` in a retry loop (`lib/go-i2p/container.go`).
- Config is `~/.go-i2p/config.yaml` generated by `GenerateRouterConfig` in
  `lib/go-i2p/config.go`.
- Upstream go-i2p **has** an I2PControl JSON-RPC server (`lib/i2pcontrol`)
  enabled by default, but bound to `localhost:7650` with HTTP and the default
  password `itoopie`. A `localhost` bind is unreachable from the host because
  the router runs in its own container netns. Its bind policy
  (`lib/i2pcontrol/server.go: validateBindPolicy`) refuses a non-loopback
  plaintext bind unless `allow_plaintext_non_loopback=true`, and refuses the
  default password on non-loopback binds.

## Live I2PControl probes (ground truth for property names)

Probe setup: i2pd 2.60.0 in a container with
`[i2pcontrol] enabled=true address=0.0.0.0 port=7650 password=<non-default>`,
HTTPS on 7650, self-signed `i2pcontrol.crt.pem` (subject/issuer
`CN=i2pd.i2pcontrol`, O=Purple I2P, no SAN, valid 10 years) generated into the
datadir on first start.

- `Authenticate` (`params: {"API":1,"Password":…}`) → success returns
  `{"result":{"API":1,"Token":"…"}}`. **i2pd quirk:** a *wrong* password
  returns `{"result":{}}` with HTTP 200 and no `error` member — a missing
  `Token` must be treated as auth failure.
- `RouterInfo` on i2pd 2.60.0 returns only the keys it supports; observed
  response for a requested set:

  | property | observed type/value |
  |---|---|
  | `i2p.router.status` | string `"0"` (a *number-as-string* in i2pd, not free text) |
  | `i2p.router.net.status` | number `2` (FIREWALLED on a single-router net — expected) |
  | `i2p.router.uptime` | number, ms |
  | `i2p.router.version` | string `"2.60.0"` |
  | `i2p.router.net.tunnels.inbound` / `.outbound` | number |
  | `i2p.router.net.tunnels.participating` | number |
  | `i2p.router.net.bw.inbound.1s` / `.15s`, `outbound.1s` / `.15s` | number, bytes/s |
  | `i2p.router.netdb.knownpeers` / `.activepeers` | number |
  | `i2p.router.net.tunnels.pools`, `i2p.router.net.connections`, `i2p.router.netdb.isreseeding`, `i2p.router.hash` | **absent from response** (i2pd 2.60 does not serve them via I2PControl) |

- **i2pd quirk:** `RouterInfo` answers even with a bad/missing `Token` (no
  auth enforcement on that method) — the dashboard still authenticates
  properly because go-i2p *does* enforce it.
- go-i2p master (`lib/i2pcontrol/handlers.go`) serves: `uptime`, `version`,
  `status` (string like `"RUNNING"`), `net.status` (number),
  `net.tunnels.participating/inbound/outbound`, `net.bw.inbound.1s/15s`,
  `net.bw.outbound.1s/15s`, `netdb.knownpeers/activepeers/fastpeers/highcapacitypeers`,
  plus netdb routerinfo counters. It **enforces** the token
  (`ErrCodeTokenNotExist -32003`, `ErrCodeAuthFailed -32001`) and returns
  JSON-RPC `error` responses for them. Endpoint paths: `/` and `/jsonrpc`.

So the dashboard requests the union of properties and tolerates missing keys
(absent → shown as `—`), and treats these as auth failures requiring
re-authentication: JSON-RPC error codes -32000/-32001/-32003/-32004, or an
`Authenticate` reply with no `Token`.

## Enabling I2PControl in the testnet (changes made in this repo)

- **i2pd** (`lib/i2pd/config.go`): `I2PControlConfig` section added to the
  struct and `GenerateRouterConfig` sets `enabled=true`, `address=0.0.0.0`,
  `port=7650`, `password=<dashboard password>`. The container IP is on the
  isolated internal bridge, and the dashboard pins trust to the router's
  generated cert (see below).
- **go-i2p** (`lib/go-i2p/config.go` + container flags): config.yaml gets
  `i2pcontrol: address: "0.0.0.0:7650"`, `password: <…>`,
  `use_https: false`, `allow_plaintext_non_loopback: true` (the network is
  internal-only; this satisfies go-i2p's bind policy explicitly instead of
  silently). The same flags are passed on the command line so they hold even
  if the config file isn't picked up, matching the existing pattern.

## Password handling

- Single source of truth: env var `GO_I2P_TESTNET_I2PCONTROL_PASSWORD` (read
  by the CLI). If unset, the CLI generates a random password per session and
  writes it to the gitignored file `logs/.i2pcontrol-password` (0600) so the
  dashboard can read it. The I2PControl default `itoopie` is rejected unless
  local-testing opt-in `TESTNET_ALLOW_DEFAULT_I2PCONTROL_PASSWORD=1` is set —
  "fail if the default password is still in use outside local testing".
- Never logged or displayed.

## TLS trust

- i2pd's I2PControl cert is self-signed (`CN=i2pd.i2pcontrol`) with no SAN, so
  normal chain verification can never succeed. The dashboard **pins** trust:
  it loads the router-generated `i2pcontrol.crt.pem` from the router's
  datadir volume (via the Docker API) and trusts *only* that exact
  certificate; everything else is rejected. An explicit
  `-insecure-tls-skip-verify` flag exists and prints a loud warning on every
  use; verification is never disabled silently. go-i2p runs plaintext HTTP on
  the internal bridge (its own policy requires the explicit opt-in above).

## Host → container reachability

Verified on this machine: the Docker host gets a route to the bridge
(`… dev br-… src 172.28.0.1`) and can open TCP connections directly to
container IPs on an `Internal: true` network (probed with `nc` and python
sockets). So the dashboard can run on the host and dial
`https://172.28.0.N:7650/` — no port publishing, no sidecar container, one
process, stdlib only.

## Integration point

`main.go`'s command loop is the launch path. The dashboard runs inside the
same `go-i2p-testnet` process: `start` boots it (unless `--no-dashboard`) and
it gets live router snapshots from the same `routers` slice — one process, no
parallel launcher. `make dashboard` (a `dashboard` subcommand of the same
binary) runs it standalone for an already-running testnet, discovering
routers from the live Docker network by container name prefix and per-router
config — still nothing hardcoded.
