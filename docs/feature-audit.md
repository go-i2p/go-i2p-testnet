# Feature audit: is go-i2p-testnet feature-complete for a testnet operator?

Audited commit: `067f30c` (working tree clean before and after; this report is the only write).
Branch: `experimental`. **This repository has no `main` branch** — `origin/HEAD -> origin/experimental`
and `refs/heads/experimental` is the only shared branch (`git ls-remote --heads origin` returns exactly
one ref). The audit was therefore performed on, and this report committed to, the default branch.

Baseline before any inspection: `go build ./...` clean, `go vet ./...` clean, `gofmt -l .` empty,
`go test -count=1 ./...` green, `go test -race -count=1 ./lib/monitor/...` green. No stop condition was
triggered: the repo builds, its suite passes, and the dashboard is present and substantial.

Method: every requirement was mapped to the code that implements it, the test that exercises it, and the
doc that claims it. The set was then re-checked against a **live testnet built from this exact tree**
(3x i2pd 2.56.0 + 1x go-i2p, driven through the interactive CLI over a pipe: `start`, `add i2pd_router` x3,
`add goi2p_router`, `sync`, `sync_netdb`), with the dashboard exercised in **both** modes — in-process
(`start`) and standalone (`-dashboard`, Docker discovery). Ground truth for contested claims was taken from
the routers themselves (raw I2PControl JSON-RPC probes, `docker logs`, container filesystem), not from
names or documentation.

---

## Verdict

**Partially complete.** All five operator capabilities are implemented and were verified live — charts
fill from real samples, the topology shows hash-matched observed edges, down/stale/recovery all behave —
but a router that is stopped and restarted is **permanently lost by the dashboard in standalone
(Docker-discovery) mode**, which is the documented operator entry point (`make dashboard`), so capability 1
("clear indication when a router is down or stale") is only conditionally satisfied.

## 3. Prioritized gap list

### Blocking

- **B-1 — A router that is stopped and restarted is permanently lost by the dashboard in standalone (Docker-discovery) mode.** `syncTargets` closes and deletes the client for a router that vanishes from discovery, but leaves `st.checkedKF` pointing at the old fingerprint ([poller.go:432-438](../lib/monitor/web/poller.go)). When the router returns with an unchanged key — same name, URL, password and pinned cert, which is exactly what `docker start` produces — the `if st.checkedKF == t.key() { continue }` guard at [poller.go:454](../lib/monitor/web/poller.go) skips client re-creation, so the router is never polled again. It renders `down` / `unreachable` / `"router removed from discovery (stopped or deleted)"` forever, with `Failures` frozen at 1 and `last_seen` frozen at the moment it stopped.
  - **Introduced by** `067f30c` (the M-2 "stopped containers stay in the roster" fix): that commit changed the vanish branch to retain `p.statuses` instead of deleting it, which is what lets the stale `checkedKF` survive.
  - **Verified live, twice, in standalone mode:** `docker stop router-i2pd-3` -> `down`; `docker start` -> still `down` 30 s later; `docker pause`/`unpause` -> still `down`, even though the router was healthy and serving I2PControl (confirmed from its own log line `Daemon: Starting I2PControl at 172.28.0.4:7650`). A **fresh** dashboard process immediately showed it `up`, proving the router was fine and the running poller had lost it. Reproduced again deterministically with `docker stop router-i2pd-1` -> `down` -> `docker start` -> `down` after 30 s.
  - **Proven deterministically** with a throwaway unit test (written, run, then deleted; tree left clean): a target removed from the source list and re-added unchanged stayed `state=down failures=1 last_err="router removed from discovery (stopped or deleted)"` after 25 further dispatches.
  - **Scope:** standalone `-dashboard` / `make dashboard` only. In CLI mode the roster is the in-memory list ([main.go:95](../main.go)), a stopped router stays in it, and the same sequence correctly produced `stale` -> `up` on restart. So the primary documented operator entry point is the broken one.
  - **Test gap:** `TestPollerPicksUpNewAndRemovedRouters` ([poller_test.go:202-237](../lib/monitor/web/poller_test.go)) drops router `a` and asserts it is kept `down`, but **never re-adds it**, so the reappear path has no coverage. The doc's own §5 stop/recover claim predates the regression and no test was added with the fix.
  - **Fix shape (not applied — this audit is read-only):** clear `st.checkedKF = ""` in the vanish branch, or key clients on presence as well as on config.

### Important

- **I-1 — go-i2p can only ever contribute inferred edges.** Sessions are read for i2pd only ([collector.go:446](../lib/monitor/dashboard/collector.go) returns nil unless `Impl == ImplI2PD`), and go-i2p publishes no `router.info` in this image — verified inside the running container: `/root/.go-i2p/config/router.info: No such file or directory` (also an open README TODO). Its roster node is therefore hash-less (`hash: ""` live) and cannot be matched by either strategy. Live: `router-goi2p-4` appeared with 3 inferred `netdb` out-edges and zero observed edges, while the three i2pd routers had 6 observed hash-matched edges. Metrics themselves work fine (go-i2p served all 15 properties including fast/high-capacity peers).
- **I-2 — four i2pd fields are permanently empty.** i2pd 2.56.0 does not serve `i2p.router.net.tunnels.inbound`, `.outbound`, `i2p.router.netdb.fastpeers` or `.highcapacitypeers` over I2PControl. Confirmed three ways: each router's own log prints `unknown request ...` for exactly those four; a direct `RouterInfo` probe returned only `knownpeers` and `bw.inbound.1s` from a five-property request (the other three were silently dropped); and the UI shows `fast_peers: null`, `high_capacity_peers: null`. Tunnels in/out are recovered via the webconsole enrich path ([collector.go:530](../lib/monitor/dashboard/collector.go), wired at [main.go:105-114](../main.go)) — verified live parsing 5 inbound / 5 outbound from the real tunnels page. Fast/high-capacity peers have no alternative source and render `not served by i2pd`, which is honest but leaves two peer-related fields unobservable for i2pd.
- **I-3 — `sync` / `sync_netdb` strand routers in standalone mode.** `syncNetDb` restarts every i2pd router ([main.go:585](../main.go)), which is a stop/start cycle. In CLI mode this is harmless (see B-1 scope), but with a standalone dashboard attached it triggers B-1: after running `sync_netdb` against the live testnet, `router-i2pd-1` went `down`/`unreachable` and stayed there. The operator's normal bootstrap step therefore silently degrades the standalone dashboard.

### Minor

- **M-1 — `Failures` counter frozen at 1 for vanished routers.** The vanish branch increments only while `State != StateDown` ([poller.go:434-438](../lib/monitor/web/poller.go)), so the "N in a row" hint ([router.html:25](../lib/monitor/web/templates/router.html)) never grows and the row looks like a one-off rather than a persistent outage. Cosmetic; a consequence of B-1.
- **M-2 — topology reports `running: true` for a router the poller considers down, with no warning.** Node liveness comes from Docker `ContainerInspect` ([collector.go:516-527](../lib/monitor/dashboard/collector.go)), which is the right authority for "is the container up", but in the B-1 state the topology page and the router table contradict each other (`state: down` next to `running: yes`) and `warnings` was empty. The demotion-to-inferred logic itself is correct and tested; it simply is not reached here because the container really was running.
- **M-3 — the index table has no per-column unit labels.** Units are baked into values (`1h 55m 38s`, `0 B/s / 0 B/s`) and headers say `BW in/out (1s)`, which is workable, but `Tunnels in/out/part` and `Peers known/active` rely on the reader parsing three numbers per cell.
- **M-4 — inferred edges are capped at 20 per router** ([topology.go:168](../lib/monitor/topology/topology.go)) with a warning when the cap binds. Correct and disclosed, but on a large unsynced roster the inferred graph is a sample, not the full adjacency.

## 4. Documentation claims that do not match the code

1. **`docs/monitoring-verification.md` §5 "Stop / recover test (deliberate)"** claims `docker start router-i2pd-2` -> `after ~12s: up` ([monitoring-verification.md:171-184](./monitoring-verification.md)). **False today in standalone mode** (B-1): live it stayed `down` indefinitely. It remains true in CLI mode, where I observed `stale` -> `up`. The claim predates `067f30c` and was not re-verified when the roster-retention change landed.
2. **`docs/monitoring-verification.md` §8** claims "The index page rendered 5 chart boxes containing 5 `<polyline>` elements; the router detail page rendered 5 polylines" ([monitoring-verification.md:228-233](./monitoring-verification.md)). Live against this tree: **3** chart boxes and **7** polylines on each page (Peers = known+active, Tunnels = in/out/participating, Bandwidth = in/out). The current code produces 3 boxes ([charts.go:77-195](../lib/monitor/web/charts.go)); the doc describes an earlier shape.
3. **`docs/monitoring-verification.md` §8 "Disruption"** claims `docker stop router-i2pd-1` demoted that router's 4 observed edges to inferred and emitted the warning `router-i2pd-1 is not running, so its sessions are not in this graph` ([monitoring-verification.md:265-273](./monitoring-verification.md)). The demotion logic exists and is unit-tested, but live I could not reproduce the warning for a stopped-then-started router: Docker reported `running: true` and `warnings` was empty (M-2). The claim is plausible for a router that is *deleted* rather than restarted; as written it is **Unverified**.
4. **`docs/monitoring-discovery.md` contradicts itself on the same four properties.** Its "Live I2PControl probes" table says `i2p.router.net.tunnels.inbound / .outbound` and `i2p.router.netdb.fastpeers / .highcapacitypeers` return `number` from i2pd 2.56 ([monitoring-discovery.md:95-99](./monitoring-discovery.md)). **Contradicted live**: all four are rejected (`unknown request ...` in every router's log; a direct five-property `RouterInfo` probe returned only `knownpeers` and `bw.inbound.1s`). The same document's later section "Why i2pd tunnel and fast/high-capacity counts cannot be filled in" gets it exactly right — `{"result":{}}` — absent ([monitoring-discovery.md:228-232](./monitoring-discovery.md)) — as does the README ([README.md:165-168](../README.md)). The early table is the stale one; the rest of the doc and the code agree with what the routers actually do.
5. **The i2pd webconsole is described as JavaScript-only, but it is server-rendered in this build.** `docs/monitoring-discovery.md:211-221` states the console's "tunnel and peer aggregates ... are fetched by its own client-side JavaScript from a JSON API this build does not expose, so there is no stdlib-only way to obtain them here", and the README repeats that i2pd "renders those aggregates on its own webconsole only via client-side JavaScript" ([README.md:167-168](../README.md)). **Contradicted live**: `?page=tunnels` and `?page=transports` return the data in the server-rendered HTML itself — I parsed 5 inbound / 5 outbound tunnel rows and a live session line (`SSU2 ( 2 ) DgzF: 172.28.0.2:4567 ... 5MZz: 172.28.0.4:4567`) out of `wget` output with no JavaScript involved. This is precisely why the webconsole scraping in [collector.go:444-459](../lib/monitor/dashboard/collector.go) and [collector.go:530](../lib/monitor/dashboard/collector.go) works. The claim is *understated* rather than dangerous — the code exploits the server-rendered HTML correctly — but it wrongly tells a reader that no stdlib-only path exists when the shipped code is using one. Note the pages are legitimately **empty** before sessions/tunnels exist (an early probe returned only the `Transports:` heading), which is a bootstrap-timing effect, not JS rendering.
6. **`README.md:138-140` "stdlib only"** is unqualified in its opening sentence while `lib/monitor/dashboard` imports the Docker SDK and `go-i2p/common`. The scoping sentence immediately after covers it, and the web/topology/i2pcontrol layers are genuinely stdlib-only, so this is imprecision rather than a false claim.

Claims I checked and found **accurate**: the 5 s interval / ~5 s per-router timeout and the concurrency model; 60-sample in-memory history and the "5 minute window" label; the four router states and the six failure classifications; certificate pinning with `-insecure-tls` as the only opt-out; password resolution order and refusal of `itoopie`; "no JavaScript / no CDN"; the observed-vs-inferred semantics and the hash-matching claim; and the §1 static-check outputs (`go build`, `go vet`, `gofmt -l .`, `go test ./...`, `go test -race ./lib/monitor/...`) — all re-run here and all green.

## 5. What was verified live, and what was not

### Verified live

A 4-router testnet (3x i2pd 2.56.0 + 1x go-i2p `0.1.0-go`) was started from this tree via the interactive CLI driven over a pipe (`start`, `add i2pd_router` x3, `add goi2p_router`, `sync`, `sync_netdb`, `dashboard`, `exit`), and the dashboard was exercised in **both** modes.

- **All routers appeared:** `totals: {routers: 4, up: 4, down: 0, stale: 0, pending: 0}`; standalone mode discovered all four from Docker (`172.28.0.2-5`) with nothing hardcoded.
- **Graphs filled in over time:** index charts grew to 20 points per box and the detail page 35 -> 60 history rows on the 5 s cadence; real timestamp x-labels; integral and byte-formatted y-axes; polylines present in all 3 boxes on both pages.
- **Topology showed edges:** 4 nodes, `observed: 6 / inferred: 3`, all observed edges `match: hash` with transport and byte counts; generation time + age rendered; solid/dashed distinction and legend present; go-i2p contributed inferred-only edges.
- **Stopped router is marked:** `docker stop` -> `down` within one interval, retained in the roster with an explanatory reason; `docker pause` -> `up -> stale (timeout) -> down` one interval apart; `docker unpause` -> `up` with failures cleared (all in CLI mode, where the router stays in discovery).
- **B-1 reproduced** twice live in standalone mode plus once deterministically in a throwaway unit test (see §3).
- **Routes and codes:** `/` 200, `/router/{name}` 200, `/router/nope` 404, `/api/status` 200, `/healthz` 200 `ok`, `/topology` 200, `/api/topology` 200, `/nope` 404, `/api/nope` 404.
- **Security:** bound to `127.0.0.1:8765` only; the live 48-char session password appeared **0** times across all five pages, the CLI/dashboard logs, `logs/*.log` and raw `docker logs` for all three i2pd routers.
- **Hygiene:** `go build`, `go vet`, `gofmt -l .`, `go test -count=1 ./...`, `go test -race -count=1 ./lib/monitor/...` all green.
- **Teardown:** `exit` removed all routers, the network and the per-router volumes (one pre-existing shared volume, `go-i2p-testnet-shared`, was left behind — consistent with the documented signal/cleanup quirk at [monitoring-verification.md:318-325](./monitoring-verification.md)).

### Not verified / Unverified

- **Very large rosters.** The 53-router run in [monitoring-verification.md:150-168](./monitoring-verification.md) was not reproduced here (4 routers only), so topology legibility, the 8 s collection budget and the 20-edge inferred cap at scale are **Unverified** — though the scaling code and its cap warning exist and are unit-tested.
- **The §8 "Disruption" topology demotion + warning** as written (see §4 item 3): **Unverified** — not reproducible for a restarted container, and container *deletion* was not tested.
- **`-insecure-tls` runtime behaviour** and **cert-pin mismatch hard failure** live: **Unverified** (unit-tested only at [pinning_test.go](../lib/monitor/i2pcontrol/pinning_test.go); I did not run with a wrong cert).
